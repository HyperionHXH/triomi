## 生产缺陷报告（复现保留为历史测试）

### B1（P1）重复导入同一备份会倍增历史记录

- **测试**：`重复导入：作品/书架/章节不倍增；历史不倍增（缺陷回归，当前失败）`
- **触发**：同一备份包 `importFromBytes` 两次，包内含同一 `(sourceId, remoteId,
  chapterRemoteId)` 的历史行。
- **预期**：历史 1 条。**实际**：2 条，每重复导入一次 +1。
- **根因**：`backup_service.dart` `_apply` 的 histories 分支只做「existing 较新
  则跳过，否则 INSERT」，而 `histories` 表主键是自增 id、复合列无唯一约束；
  时间相同的重放（isAfter=false）必然再插一行。普通阅读路径
  `LibraryRepository.recordHistory` 是先删后插，所以平时不暴露。
- **影响**：备份/同步重放会污染阅读历史与「最近阅读」排序。
- **建议**：对齐 `recordHistory` 语义——导入前先删除同 `(sourceId, remoteId,
  chapterRemoteId)` 的旧行再插入；或给 histories 建 `user_version=3` 迁移加唯一索引。

### B2（P1）备份导入侧不过滤敏感键

- **测试**：`导入侧敏感键过滤（缺陷回归，当前失败）`
- **触发**：手工构造的包（或未来格式变更/第三方工具产出的包）在
  `settingsValues` 里携带 `lk.securityKey` / `tracking.bangumi.token`。
- **预期**：导入侧与导出侧同样按 `BackupService._isSensitive` 过滤。
  **实际**：`preferences.importAll` 原样写入，credential 形状的键进入 Hive。
- **影响**：F1 红线在「外来包」入口破口；_secure store_ 不受影响（凭据正身在
  secure store，Hive 只是迁移前回退），但键值仍被写入了不应写入的位置。
- **建议**：`_apply` 的 settings 导入复用 `_isSensitive` 过滤（一行改动 +
  本回归即可转绿）。

### B3（P2）缺 `updatedAt` 的书架行按「当前时间」参与合并

**复核状态（2026-10-02）**：已改为按 Unix epoch 最旧时间处理，并新增回归；缺时间戳的备份不会覆盖本机较新进度。

- 测试内现状断言（通过）：缺时间的包等价于「刚更新过」，会覆盖本机较旧进度。
  若远端包缺时间但内容其实更旧，本机进度会被旧值覆盖。建议缺时间按「更旧」
  或要求导出方必填（现状先固化，交 Codex 决策）。

### 发现 4（P3，不改行为）

- `WebDavClient.ensureDirectory` 对 MKCOL 的所有 `SourceException` 都吞掉
  （只显式处理 405），401/网络错误不提前暴露；最终 PUT 仍会失败并抛出，
  不构成「失败报成功」，但错误延迟一层。建议非 405 异常重抛。
