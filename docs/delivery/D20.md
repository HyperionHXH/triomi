## 覆盖清单（11 例）

**并发时序**：
- 早请求晚返回：两个在途上报同时停在网关上（各发首个请求、无回执），释放后
  都成功，markSynced 只前进不后退；
- 进度连发 1→2→3：PATCH 的 `episode_id` 集合为 [101]、[101,102]、[101,102,103]
  ——连发不回退、单调增长；
- 一服务成功另一服务失败：Bangumi 500 / AniList 成功 → 逐项结果独立，
  AniList 的 syncedAt 前进而 Bangumi 不动。

**markSynced 时机**（参数化 401 / 429 / 超时）：
- 失败后 syncedAt 保持基线不变（失败绝不 markSynced）；
- 重试成功后才更新为更晚的时间。

**解绑与凭据竞态**：
- 在途上报期间 `unbindAll` → 释放回执 → 结果 ok 但 `bindsFor` 为空：
  `markSynced` 是纯 UPDATE（`tracking_repository.dart:96`），旧回执不会重建
  已解绑记录；
- 在途上报期间 `clearToken` → 本次按发起时捕获的 token 完成（Authorization
  只在请求里出现一次），下次上报明确失败「未配置 access token」且不再发请求
  ——凭据不泄漏到下一账号。

**进度映射**（服务层，客户端层契约在 D9）：
- 番剧小数进度 2.5 → floor 2 → PATCH [101,102]；
- 远端已看 5 > 本地 2 → 只增不减跳过（0 次 PATCH）；
- 剧集目录缺 `ep` 的条目按已解析条数补号参与映射（id 102 补为第 2 集）；
- 两来源相同 remoteId（lk/1 与 lns/1 都绑 Bangumi 12）：上报只更新本来源的
  syncedAt；小说走 `ep_status`（无 PATCH）。

## 实际调用顺序与存储结果（交付要求）

`reportProgress`（番剧）实际顺序：`GET /v0/users/-/collections/12/episodes?limit=200`
（远端已看数）→ 若本地 ≤ 远端直接返回 → `POST /v0/users/-/collections/12`
（状态）→ `GET /v0/episodes?subject_id=12`（目录）→ `PATCH /v0/users/-/collections/12/episodes`
（逐集标记）→ `markSynced`。小说顺序：`GET collections/12`（现行收藏）→
`POST /v0/users/-/collections/12`（ep_status）→ `markSynced`。存储结果均为
`track_binds.syncedAt` 单列更新；失败路径该列不变。

测试期间发现的精度坑（非缺陷）：drift 把 `DateTime` 按秒存，
`bind()` 与紧随的成功上报可能落在同一秒，`isAfter` 断言会抖动——测试用
「基线显式置为过去」解决，生产语义不受影响。
