## 真实 runtime timeout 作用范围（交付要求的实证区分）

**结论：超时只覆盖异步 promise 的排空，不覆盖同步执行——同步无限循环不可
被中断，规则不是安全沙箱。**

- 静态证据（本机无可靠的子进程注入手段，未做子进程实证，按工作单提交静态
  证据与风险）：
  - `js_runtime_factory_io.dart` 的 `call()`：`runtime.evaluate('__triomiCall(...)')
    是**同步**调用，没有任何超时参数；随后 `runtime.handlePromise(evaluated,
    timeout: 30s)` 的超时只作用于 promise 微任务排空循环
    （`js_runtime_factory_io.dart:155` 附近的 `on TimeoutException`）。
  - flutter_js 的 `evaluate` 无超时能力（其 API 即同步阻塞）——规则里的
    `while(true){}` 会把宿主 isolate 永久挂住；D22 工作单也明确禁止在测试
    主进程里验证这一点。
- 风险表述（**不是**「沙箱完全安全」）：规则代码在引擎里拥有与宿主回调同
  等的执行权，恶意/坏规则可以造成同步挂死；防线只有规则来源可信（用户自行
  导入）与来源注册表里的失败可见性。若未来要硬防护，需要把引擎放进独立
  isolate 并做看门狗——属生产改动，归 Codex 决策。

### D22-1（P2）宿主连接类错误把完整 URL（含 query 凭据）透传到来源失败列表

- **测试**：`连接失败的错误文本不携带 URL 查询串里的凭据（缺陷回归，当前失败）`
- **触发**：JS 规则 `triomi.fetch('https://host/api?token=…')` 且请求在连接层
  失败。真实网络层 `SourceException.wrap`（`source_exception.dart:35`）把
  `url：原因` 整段放进 message；`_JsHttpBridge` → `JsSource._invoke` 原样透传
  到来源失败列表（用户可见）。
- **预期**：错误输出剥掉 URL 查询串（或整段 URL）。**实际**：message 含
  `token=…` 全文。
- **影响**：F1 红线的边缘破口——凭据进入 UI/日志/崩溃报告。
- **建议**：在 `JsSource._invoke` 透传 hostError 前，或更根本地在
  `SourceException.wrap` 拼 url 前，按 D11 同款规则剥掉 query/fragment。
