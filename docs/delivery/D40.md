## 覆盖清单（5 例）

1. 多条 pending（3）+ wifiOnly + 非 WiFi → 无任务执行、泵停住
   （resolver 调用数停止增长）；
2. **1 条 pending + wifiOnly + 非 WiFi：泵必须停住而不是自旋（缺陷回归，
   当前失败，见下）**；
3. 多条 pending + WiFi → 全部执行到 done、队列清空；
4. 1 条 pending + WiFi → 执行到 done，泵自然退出（调用数不再增长）；
5. 停泵后切回 WiFi → `resume()` 恢复执行剩余任务到 done。

测试通过 `ProviderContainer` + `databaseProvider`/`preferencesProvider`/
`sourcesProvider`/`downloadServiceProvider` override 装配，等待用真实时间
窗口轮询（`waitFor`），不依赖 widget 测试的 FakeAsync。

## 生产缺陷报告（复现保留为失败测试）

### D40-1（P1）单任务 + 仅 WiFi + 非 WiFi 时调度器在纯微任务层无限自旋

- **测试**：`1 条 pending + wifiOnly + 非 WiFi：泵必须停住而不是自旋`
- **触发**：`wifiOnly` 开启、网络处于非 WiFi（如移动数据/断网）、队列里**恰好
  剩 1 条** queued 任务时触发 `_pump`。
- **预期**：泵像多任务场景一样 break 停住。**实际**：`_pump` 的停泵守卫是
  `service.wifiOnly && pending.length > 1 && !await service.isOnWifi()`
  （`download_providers.dart:137`）——单任务时 `pending.length > 1` 为 false，
  守卫被短路；而 `run()` 已经把任务重新标回 queued 并抛出 WiFi 异常（被吞）。
  循环回到 `pending()` → 同一条任务 → 再次拒绝 → **无限循环**。
- **危害放大**：`NativeDatabase`（以及真机上的 drift 查询回调）在微任务层
  完成，这个自旋是**纯微任务循环**——事件循环的定时器全部饿死
  （测试运行时表现为整个进程挂死，任何 `Future.delayed` 都不会触发）。
  用户场景：仅 WiFi 下载开启 + 断网/流量下手动入队 1 章 → UI 卡死。
- **复现记录**：初版测试用真实时间窗口等待即整体挂死（后台任务被强制终止）；
  改为 resolver 熔断器（第 25 次调用起切回 WiFi）后测试可终止并量化自旋
  （调用数冲破阈值 vs 正确实现的个位数）。
- **建议**：把守卫改为 `pending.length >= 1`（单任务也要停），或在 `run()`
  抛 WiFi 异常后直接 break——两种修法都让本回归转绿；生产代码改动归 Codex。
